## 5. 설계 결정과 대안

### 선택

`docs/superpowers/plans/2026-07-16-db-001-layered-enforcement.md`에 11개 순차 task를 작성했다. project-local checksum CLI, PostgreSQL-only Supabase config, 4 forward migration과 4 compensation, 5 pgTAP suite, lazy typed FastAPI repository, local-only concurrency test, explicit Docker DB gate, 최종 docs/version/handoff를 각각 독립 commit·review 단위로 둔다.

### 이유

DB-001은 tooling, DDL, 권한, 상태 전이, 보관, Python 호출 경계가 연속해서 맞아야 한다. 각 task에서 RED→최소 구현→GREEN→commit을 끝내면 SQL 오류·권한 누락·backend drift를 다음 단계 전에 발견하고 task commit 단위로 안전하게 되돌릴 수 있다.

### 고려했지만 선택하지 않은 대안

- 즉시 migration 구현: 사용자의 계획 검토 gate와 저장소 지침을 위반하므로 제외.
- global/npm CLI install: exact asset/digest와 lifecycle 통제가 약해 제외.
- full Supabase service stack: DB-001에 auth/storage/studio/analytics가 불필요하고 PC 자원을 더 쓰므로 PostgreSQL-only config 선택.
- PostgREST/browser RPC: local/private backend-only 경계와 충돌하므로 Data API disabled 유지.
- backend repository를 이후 chat slice로 전부 미루기: D-025의 DB+backend 이중 강제를 DB-001에서 검증하지 못하므로 lazy internal boundary까지 포함.
- 공식/mock seed 포함: PM 승인과 DATA-SEED-001 lineage를 우회하므로 제외.

### 2026-07-16 실행 호환성 명확화

계획 승인 당시의 "PostgreSQL-only config" 결정은 유지한다. 구현 중 pinned Supabase CLI
v2.109.1의 bare `supabase start`가 `api.enabled=false`여도 persistent Kong gateway를 시작할 수
있음이 확인됐다. 따라서 계획의 시작 명령은 `supabase db start`로 바로잡았다. pgTAP의
`supabase test db`가 검사용 일회성 `pg_prove` container를 사용할 수는 있지만, persistent
project runtime은 PostgreSQL container 하나만 허용한다. 이는 제품 범위·공개 계약·DB schema를
바꾸는 새 결정이 아니라 승인된 local-first/PostgreSQL-only 의도를 실행 도구에 정확히 맞춘
내부 호환성 보정이다.

## 12. AI 내부 구현 세부 — 필요할 때만 보면 되는 내용

- CLI pin manifest와 bootstrap을 schema보다 먼저 테스트해 supply-chain과 local path를 고정한다.
- migration은 private schema → invariants → capabilities/functions → indexes/read interfaces 순서다.
- `app_api`는 enum-shaped 값을 text allowlist로 받고 내부 cast해 backend에 `app_private` schema/type usage를 주지 않는다.
- compensation은 그 역순이며 absence proof 후 fresh replay한다.
- backend는 pool을 import/open하지 않고 `open=False` factory와 typed repository만 준비한다.
- SQL function signature와 Python call placeholder 수를 plan에서 일치시켰다.
- root no-Docker gate와 explicit Docker DB gate를 분리해 평상시 검증의 안정성을 유지한다.
