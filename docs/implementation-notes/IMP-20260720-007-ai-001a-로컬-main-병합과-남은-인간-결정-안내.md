## 5. 설계 결정과 대안

### 선택

- remote가 없으므로 pull/push/PR 없이 local `main`에 `git merge --ff-only`를 사용했다.
- 병합 성공·HEAD 확인 뒤 저장소 내부 소유 worktree만 제거하고 기능 브랜치를 `-d`로 삭제했다.
- cleanup 중 정상 `git worktree remove`가 Windows pnpm 잔여를 남겨, registration prune 뒤 exact
  path dry-run을 확인하고 `git -c core.longPaths=true clean -fdx -- <exact-path>`로 마감했다.
- 삭제된 ignored 도구는 사용자 계정의 exact uv 0.11.28을 hash-equal copy하고, approved tracked
  bootstrap으로 Go 1.25.11·Supabase v2.109.1 두 독립 build를 재생성해 runtime manifest hash를 맞췄다.
- IMP-006 재현 절차와 AI-001A plan에 `.tools` junction 금지와 byte-copy/hash/`-VerifyOnly`를 추가했다.

### 이유

fast-forward는 검증된 commit 계보를 그대로 보존하며 예상 밖 merge commit이나 충돌을 차단한다.
cleanup은 삭제 대상을 저장소 내부 단일 worktree로 제한하고 먼저 dry-run해 다른 사용자 파일을
건드리지 않았음을 확인할 수 있다.

### 고려했지만 선택하지 않은 대안

- PR: remote가 없어 불가능하고 사용자가 local merge를 선택했다.
- squash/rebase: 검증된 RED→GREEN task commit 계보와 해시를 바꾸므로 사용하지 않았다.
- worktree/branch 유지: 선택지 3이 아니므로 정리했다.
- 강제 branch 삭제: 정상 병합됐으므로 `git branch -d`로 충분했다.

- 추천 A: DB 권위는 유지하고 같은 승인 데이터 19/3/10을 담은 수정 release `.2`를 새로 만든다.
- 의미: `.1`을 몰래 고치지 않고 새 version·manifest·technical approval·전체 actual DB cycle로
  수정하므로 추적성과 rollback이 명확하다.
- 선택 B의 위험: 글로벌 DB role membership를 migration으로 바꾸므로 보안 영향이 더 크다.
- 결정 전 상태: official DB row 0, `/ready=503`, AI-001/LLM/chat pipeline Blocked.

### Q-PII-002 — chat consumer 명세 전에 결정

- 문제: core가 위험 입력을 text 없이 안전 차단해도 시민에게 어떤 말과 reason을 반환할지 없다.

  질문해 주세요”라는 재질문 안내를 제공한다.
- 의미: 시스템 장애가 아닌 개인정보 안전 정책 outcome으로 KPI·감사를 정확히 분리한다.
