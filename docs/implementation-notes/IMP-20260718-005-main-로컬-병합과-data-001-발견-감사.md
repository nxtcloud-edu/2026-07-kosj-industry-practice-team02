## 5. 설계 결정과 대안

### 선택

- 사용자가 고른 finishing option 1에 따라 local `main`으로 fast-forward했다.
- main에는 ignored runtime을 복사하지 않고 승인된 `bootstrap_patched_supabase.ps1 -Install`을
  한 번 실행해 source부터 재현했다.
- 공식 출처 감사와 main 검증은 tracked 파일을 공유하지 않는 3개 독립 범위로 병렬화했다.
- DATA-001은 source audit와 artifact gap 보고까지만 수행하고, PM 승인 전 official dataset,
  ACTIVE seed, readiness, 제품 코드는 변경하지 않았다.

### 이유

fast-forward는 feature의 검증된 commit graph를 그대로 유지한다. runtime 재빌드는 ignored
binary 복사보다 source/tag/patch/Go/binary pin을 다시 증명한다. 출처 감사는 DRAFT 작성 전에
구 URL·동적 사실·약한 기관 매핑을 발견해 공식 데이터 오염을 예방한다.

### 고려했지만 선택하지 않은 대안

- merge commit 강제 생성: 별도 분기 이력이 필요하지 않고 fast-forward 가능해 불필요했다.
- feature worktree의 ignored binary 복사: 재현성 증거가 약해 선택하지 않았다.
- 출처대장 수치·URL을 바로 수정하거나 SQL seed 작성: staging/PM 승인 경계를 우회해 금지했다.
- CSV에 구조화 array를 JSON 문자열로 넣어 곧바로 authoring: artifact 설계 승인 전이라 보류했다.
