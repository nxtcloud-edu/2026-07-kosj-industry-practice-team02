## 5. 설계 결정과 대안

### 선택

먼저 1회성 협업 기반을 구축한 뒤 Frontend와 Backend/Data 작업을 병렬화한다.

### 이유

현재 remote/CI 없이 제품 코드를 더 늘리면 팀원이 같은 기준을 clone·검증·병합할 수 없고 해외에서
Cloud/local 연속성도 없다.

### 고려했지만 선택하지 않은 대안

- 즉시 chat/admin 제품 코딩: remote/ownership/CI가 없어 충돌 위험이 큼.
- 공개 배포: 별도 보안·DB·CORS·비용 승인 전 금지.
- Cloud에 DeepSeek/DB secret 등록: 현재 local-only 정책 위반.

## 6. 구현 상세

승인 시 구현하는 것:

1. 값 비노출 Git history scanner와 테스트.
2. Frontend self-merge exact 경로 classifier와 append validator.
3. PR/Issue template, 항상 실행되는 secret/contract/docs·JSON 검사와 Frontend CI.
4. Playwright Windows/Linux portability 보정.
5. private GitHub `origin/main`, collaborator/repository 변수 설정.
6. repository 하나로 제한된 secret 0 Codex Cloud 환경.
7. 팀원 self-merge와 Cloud Draft PR 리허설.
8. 최종 운영 문서·구현 노트·증거.

구현하지 않는 것: 실제 chat 응답, DeepSeek adapter 활성화, DB seed/READY, `/admin`, 공개 배포.

협업 기반 뒤 제품 순서는 `DATA-SEED-002 → READY → PII consumer/AI 검색·응답 → API-CHAT`이며,
Frontend 팀원은 병렬로 fixture 기반 chat UI를 진행하고 계약 준비 뒤 실제 연결·admin으로 이어간다.
