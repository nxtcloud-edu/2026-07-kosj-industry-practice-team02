## 5. 설계 결정과 대안

### 선택

진행률을 세 층으로 보고한다.

1. product code-present: 실제 P0/P1 기능 가중치로 필요한 코드가 존재하는가 — 약 20%.
2. evidence-tested: 현재 직접 또는 제한된 역사 증거로 검증됐는가 — 약 15~20%.
3. demo-ready: 시민 질문부터 관리자 승인 후 재질의까지 도달 가능한가 — 0%.

제품 기능 가중치는 governance 문서 자체에 0을 주고, 사용자가 실제로 경험하거나 이를 직접
지탱하는 실행 계층만 다음처럼 계산했다.

| 제품 capability | 최종 가중치 | 현재 실행 가능 코드 추정 | 가중 기여 |
|---|---:|---:|---:|
| 시민 grounded chat·FOLLOWUP·fallback | 30 | 5% | 1.50 |
| 관리자 실패→후보→승인→재질의 | 25 | 15% | 3.75 |
| 공식 data·seed·readiness | 15 | 5% | 0.75 |
| 접근성·평가·성능·demo·backup·handoff | 15 | 5% | 0.75 |
| platform·health·contracts·safe logging | 10 | 85% | 8.50 |
| DB 실행 foundation·runtime gate | 5 | 70% | 3.50 |
| **합계** | **100** | — | **18.75 → 약 20%** |

DB와 platform은 중요하지만 최종 제품 가중치의 15%만 차지하게 해 내부 작업량이 시민/관리자
기능을 덮어쓰지 않도록 했다. 반대로 commit·문서·계획 활동까지 보는 저장소 성숙도는
25~30%로 별도 해석할 수 있으나 사용자 제품 완료율로 쓰지 않는다.

실행은 다음 세 track으로 제한한다.

- Track A: patched CLI → DB full gate. 내부 순서는 절대 병렬화하지 않는다.
- Track B: 공식 KB/기관/매핑 작성과 PM 승인. 별도 worktree에서 Track A와 병렬 가능하다.
- Track C: `/` 완성·공통 접근성 UI shell. 공개 계약을 건드리지 않는 범위에서 병렬 가능하다.

각 수직 흐름은 implementer 뒤 spec/quality reviewer 두 명을 병렬로 붙이고, 둘 다 통과하기 전 다음
공유 계약·schema 단계로 넘어가지 않는다.

5시간 block은 벽시계 5시간 동안 root coordinator 1개와 최대 3개 agent가 동시에 일하는 단위다.
따라서 한 block은 최대 약 20 team-hours(5 coordinator-hours + 15 subagent-hours)일 수 있으며
다음 배분은 외부 PM 대기시간을 포함하지 않는다.

| 구간 | coordinator block | 병렬화·종료 조건 |
|---|---:|---|
| patched CLI·actual DB gate + DATA 초안 + HOME | 1~3 | 세 track 병렬; DB stop 발생 시 Track A만 재계획 |
| 승인 data seed·readiness | 1 | DB와 PM 승인 data가 모두 있어야 시작 |
| PII·분류·검색·template·LLM + chat API/UI | 2~4 | 계약 고정 후 backend/frontend 병렬 |
| event·failure·admin·approval·REG-01 | 2~3 | 상태 머신 순서는 직렬, API/UI는 경계별 병렬 |
| A11Y·평가·성능·backup·demo·handoff | 2~4 | 독립 검증을 병렬화하되 최종 gate에서 합류 |
| **전체 local P0/P1** | **8~15** | PM 검수 지연·새 인간 결정·실패 repair block 제외 |

### 이유

현재 전체 backlog의 Done은 발견·기반·계약에 집중돼 있고 시민 chat/admin P0/P1은 모두 Blocked다.
DB/data/chat을 같은 worktree에서 동시에 수정하면 migration, generated contract와 테스트 증거가 충돌한다.
반면 data authoring과 home shell은 DB tooling과 파일·상태가 독립적이라 별도 worktree 병렬화 이득이 크다.

### 고려했지만 선택하지 않은 대안

- 문서/commit 수로 완료율 산정: 긴 DB·tooling 이력이 실제 사용자 흐름을 과대평가하므로 제외했다.
- 3개 agent가 같은 schema/API를 동시에 구현: merge 속도보다 review·rollback 위험이 커서 제외했다.
- Task 2C를 건너뛰고 Task 3 build 재시도: 승인된 path safety gate를 우회하므로 금지한다.
- public deployment 병행: A-021, admin authentication, CORS/log/secret/backup 결정이 없어 제외한다.
