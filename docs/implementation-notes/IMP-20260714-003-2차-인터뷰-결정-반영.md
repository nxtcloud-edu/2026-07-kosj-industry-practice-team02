## 5. 설계 결정과 대안

### 선택

1. DeepSeek는 서버가 allowlist로 확인한 합성 fixture에만 사용하고 client `is_test`는 신뢰하지 않는다.
2. 실제 시민·PII·민감정보·public 요청은 DeepSeek로 보내지 않고 ACTIVE KB template/disabled 경로를 사용한다.
3. Supabase CLI의 `supabase/migrations/`를 실행 권위로 삼고 논리 SQL 초안은 참고본으로 유지한다.
4. 이름·상세주소는 보수적으로 가리며 성능 저하가 있어도 자동으로 완화하지 않는다.
5. 200 `ChatResponse`는 SUCCESS/FOLLOWUP/FALLBACK만, 안전 대체 없는 시스템 불능은 503 `SERVICE_UNAVAILABLE`로 구분한다.
6. 원격/CI 대신 동일 검사 명령을 local 완료 gate와 구현 노트 증거로 강제한다.
7. 대화 기억은 화면상 transcript, 요청 간 문맥, 서버 영속 저장을 별개로 보고 최종 결정을 보류한다.

### 이유

- DeepSeek 공식 문서는 context caching이 기본 활성화되고 입력 prefix가 수 시간~수일 디스크에 남을 수 있다고 명시한다. 실제 시민 데이터를 보내지 않는 것이 사용자의 합성 데모 의도와 privacy 원칙을 가장 정확히 지킨다.
- 이 제품의 사실성은 모델 추론이 아니라 ACTIVE KB 근거 gate와 서버 출처 결합에서 나오므로 disabled/template 경로가 항상 필요하다.
- provider 장애 자체가 503이면 안전한 KB template이 있어도 불필요한 장애가 된다. 안전 응답 완성 가능성이 올바른 경계다.
- Supabase 기능(RLS/trigger/function)을 SQL 한 계보로 관리하는 것이 Alembic 혼합보다 단순하다.

### 고려했지만 선택하지 않은 대안

- `deepseek-chat`/`deepseek-reasoner` alias: 2026-07-24 종료 예정이라 새 구현에서 제외.
- 실제 시민 입력을 마스킹 후 DeepSeek에 전송: cache·보관·국외 처리·법적 근거가 별도 승인되지 않아 제외.
- Alembic+SQLAlchemy: RLS/trigger/function은 결국 수동 SQL이 필요하고 새 production dependency가 늘어 제외.
- 마스킹 B 자동 전환: 개인정보 계약을 AI가 자동 완화하게 되어 제외.
- 모든 장애를 200 또는 모든 provider 장애를 503: 정책 결과/transport 의미 또는 safe degradation을 왜곡해 제외.
- remote/CI 임의 생성: 사용자가 명시적으로 나중에 연결하겠다고 해 제외.
- Q-CHAT을 무상태로 임의 확정: 사용자가 챗봇 경험 우려와 설명 요청을 밝혀 제외.

### 데이터 흐름/상태 변화

```text
server-allowlisted synthetic fixture
→ conservative PII mask
→ ACTIVE KB minimum context
→ Q-LLM-004에서 승인된 DeepSeek V4 model
→ JSON schema validation
→ max 1 retry
→ server source metadata / template fallback

→ conservative PII mask + ACTIVE KB retrieval
→ DeepSeek adapter blocked
→ deterministic template or safe fallback
```

- 애플리케이션/DB 데이터, 공식/mock 레코드, API key, provider payload는 생성하지 않았다.

### 오류·빈 상태·롤백

- provider 실패+ACTIVE KB 안전 template 가능: 200 SUCCESS/FALLBACK.
- 필수 근거 경로 불능+안전 대체 없음: 503 stable envelope.
- 프론트 503 상태는 loading 해제, 중복 재시도 방지, 키보드 재시도, 내부 상세 미노출이다.
- 실제 앱/migration/data가 없어 이번 변경의 rollback은 문서·draft version rollback만 해당한다.

## 9. 보안·개인정보·접근성·성능 영향

- Privacy: raw 시민 질문·실제 PII를 생성·저장·전송하지 않았다. DeepSeek는 합성 allowlist 전용이며 default disk cache와 불명확한 전체 보관/학습 보장을 문서화했다. 보수적 이름·주소 마스킹과 불확실 시 provider 차단을 확정했다.
- Security: API key는 backend env only, value/balance 기록 0. public/real-user provider 호출 금지, client `is_test` 불신, 503 body의 provider/stack/body 미노출을 계약했다.
- Accessibility: UI 코드는 없다. 503 재시도 상태의 loading 해제·중복 방지·키보드 접근 인수 기준만 추가했다.
- Performance/cost: 외부 호출 0, 새 비용 0원. Flash/Pro와 app hard cap은 미정이며 무응답 시 provider disabled다. provider 장애에도 KB template이 가능하면 200으로 degrade해 데모 안정성을 높였다.

## 11. 인간이 반드시 알아야 하거나 승인할 내용

1. DeepSeek는 “실사용 안 함” 결정에 맞춰 합성 fixture에만 사용한다. 실제 시민 질문을 보내는 제품으로 확대하려면 개인정보 고지·국외 처리·보관·법적 근거를 새로 승인해야 한다.
2. Q-LLM-004에서 V4 Flash/Pro와 잔액 보호 hard cap을 정해야 한다. 그 전에는 DeepSeek 호출이 비활성이다.
3. Q-CHAT-001에서 브라우저 전달형 짧은 문맥과 서버 TTL 세션 중 하나를 정해야 한다. 화면에 이전 메시지를 보여주는 것과 서버 저장은 같은 문제가 아니다.
4. API draft는 승인된 200/503 behavior 때문에 0.2에서 1.0으로 major 변경됐다. 아직 구현 소비자는 없다.
5. Docker engine off, Supabase CLI/pnpm/uv 미설치, 기본 Python 3.14로 현재 승인 toolchain을 바로 실행할 수 없다. 최종 계획 승인 뒤 설치/고정한다.
6. 원격/CI가 없으므로 local backup과 수동 검증 증거 누락 위험이 있다. 사용자가 Git 연결을 요청할 때 다시 결정한다.
7. 아직 계획은 `Interviewing`이다. 사용자의 `진행`/`구현 시작` 전 Git init·설치·제품 코드를 시작하지 않는다.

## 12. AI 내부 구현 세부 — 필요할 때만 보면 되는 내용

- 공개 오류 code는 provider/DB별 세부 code 대신 `SERVICE_UNAVAILABLE` 하나로 안정화하고 내부 cause만 구조화 로그에서 구분했다.
- `interaction-event.schema.json`의 SYSTEM_ERROR는 유지하고 시민 200 response schema에서만 제거했다.
- SQL 자동 down을 가정하지 않고 reset/replay+보상 SQL로 계획 문구를 바꿨다.
- 문서 링크, 표 상태, dependency 이름, exact enum 같은 내부 정합성은 승인된 행동 안에서 자율 동기화했다.
