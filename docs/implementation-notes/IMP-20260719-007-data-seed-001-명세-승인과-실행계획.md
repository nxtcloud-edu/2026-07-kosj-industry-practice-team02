## 5. 설계 결정과 대안

### 선택

- 명세 승인과 계획 승인을 분리하고 이 요청에서는 계획까지만 작성한다.
- initial release는 19/3/10, fixed governance timestamp, create-once filesystem authority를 사용한다.
- generator/publisher/DB verifier/PowerShell orchestrator를 분리하고 dependency-free Python과 기존
  psycopg/patched Supabase만 사용한다.
- actual verification은 forced rollback, second seed, compensation guard, two concurrency ordering,
  seed→compensation→seed와 semantic hash를 포함한다.

### 이유

파일 승인·publication·DB mutation의 실패 경계를 분리해야 immutable release를 손상하지 않고
prepared-but-inactive 상태와 transaction rollback을 명확히 복구할 수 있다. 기존 migration/role/API를
바꾸지 않아 public-security scope와 비용을 늘리지 않는다.

### 고려했지만 선택하지 않은 대안

- 지금 즉시 release/seed 구현: 명시적 plan approval gate 위반이라 제외했다.
- DB release ledger/migration: 새 privilege/schema/public security review가 필요해 initial local slice에서 제외했다.
- 직접 `supabase/seed.sql` 편집: approval hash와 immutable lineage가 끊겨 제외했다.
- non-empty/live DB compensation: 운영/reference data 삭제 위험 때문에 명시적으로 금지했다.
- ambient `now()` timestamp: reproducibility를 깨므로 승인 시각 literal로 고정했다.
