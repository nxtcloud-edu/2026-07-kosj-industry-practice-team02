# DATA-SEED-001 immutable official release and local seed design

- Status: Review — Q-SEED-001=A architecture approved; written specification approval pending
- Date: 2026-07-19
- Owner: Backend·Data·Security
- Related: D-036, A-028, ADR-0015, ADR-0016, DATA-001 `0.1.0-draft.1`

## 1. Goal

Promote only the PM-approved projection of DATA-001 into an immutable, reproducible official-data
release and load it into the existing disposable local PostgreSQL schema without a new migration.
The release must remain auditable from the approved staging bytes and must fail closed before any
partial or destructive import.

The first release version is exactly `0.1.0-initial.1`. It contains 19 ACTIVE/OFFICIAL KB records,
3 OFFICIAL offices and 10 approved office-service mappings. `KB-WASTE-03`,
`OFFICE-AREUM:LOCAL_TAX_GENERAL`, `OFFICE-DODAM:BULKY_WASTE` and every mock record are excluded.

## 2. Non-goals

- No new DB table, function, role, RLS policy, migration or public API contract.
- No `/ready=200`, retrieval, citizen answer, admin UI or LLM change; READY-001 and AI-001 remain
  later vertical slices.
- No promotion of a PENDING/REJECTED/stale-hash/self-approved manifest.
- No in-place edit or deletion of an immutable release.
- No compensation against a non-empty, referenced or remotely operated database.
- No WASTE-03 activation before REG-001 and a later PM-approved release.

## 3. Inputs and trust boundary

The only promotion input is the canonical directory
`data/staging/data-001/0.1.0-draft.1/`. Promotion is allowed only when all of these are true:

1. `approval_manifest.json.state == APPROVED_FOR_INITIAL_RELEASE`.
2. `reviewed_by == PM-LOCAL-001`, `reviewed_at` is timezone-aware, dataset comment is non-empty,
   and reviewer differs from `AI-DATA-BACKEND`.
3. All 35 decisions and comments are non-empty and the approved projection is exactly 19/3/10,
   with WASTE-03 withheld and the two named mappings rejected.
4. The manifest hashes and counts match the three current content files.
5. The current DATA-001 schema/source/privacy/runtime-isolation validator passes.

Approval comments are governance evidence. They are copied into the immutable approval artifact but
never inserted into application tables or audit logs.

## 4. Release layout and ownership

```text
data/official/releases/0.1.0-initial.1/
  release_manifest.json
  approval_manifest.json
  kb_records.json
  offices.json
  office_service_mappings.json
  seed.sql
  compensation.sql
```

- The directory is create-once. If it already exists, preparation exits non-zero without changing a
  byte, even if the requested output appears identical.
- A corrected release always gets a new semantic pre-release or patch version. Released bytes are
  never edited or deleted in place. This slice is initial-release-only and accepts exactly
  `0.1.0-initial.1`; any successor version or transition over an already seeded DB requires a new
  human-approved design and plan.
- `supabase/seed.sql` becomes a generated byte-identical dispatcher copy only in the separate local
  activation phase. A prepared release with a different dispatcher is valid but not locally active;
  the active verification gate rejects drift between the two paths.
- `data/schemas/data-seed/v1/` owns the release-manifest and projected-content contracts.
- `docs/data-lineage/DATA-SEED-001-0.1.0-initial.1.md` records draft hashes, approval hash, release
  hashes, transformation version, DB verification and rollback boundary.

## 5. Release manifest

`release_manifest.json` is canonical UTF-8/LF/two-space JSON with sorted object keys where the
repository serializer requires them and a trailing newline. It contains exactly:

- `schema_version: 1`
- `release_id: sejong-official-0.1.0-initial.1`
- `release_version: 0.1.0-initial.1`
- `source_draft_version: 0.1.0-draft.1`
- `released_at`: an explicit timezone-aware CLI input recorded in lineage; never ambient `now()`
- `approval`: path, SHA-256, reviewer ID and reviewed timestamp
- `artifacts`: lexical path, record count and SHA-256 for the three projected JSON files, `seed.sql`
  and `compensation.sql`
- `projection`: KB 19, office 3, mapping 10, withheld KB 1, rejected mapping 2, mock 0
- `seed_semantic_sha256`: SHA-256 of the exact canonical seed-owned DB projection defined below
- exact excluded record IDs and the generator/version identifier

The manifest contains no citizen question, answer, transcript, token, provider payload, secret or
private administrative data.

### Release JSON contracts

`data/schemas/data-seed/v1/` contains four Draft 2020-12 schemas. Every object has
`additionalProperties: false`; arrays use canonical lexical public-ID/key ordering; validators reject
duplicates and require cross-file references to resolve.

- `release-manifest.schema.json`: the exact fields in this section, including artifact path/count/hash,
  approval reviewer/timestamp/hash, projection counts, excluded IDs and generator ID.
- `kb-records.schema.json`: `schema_version`, `release_version`, and records with every staging KB
  content/source field plus `status=ACTIVE`, `data_origin=OFFICIAL`, `created_by`, `approved_by`,
  `approved_at`, and all authored `question_examples`.
- `offices.schema.json`: `schema_version`, `release_version`, and records with every public office and
  source-provenance field plus `data_origin=OFFICIAL`, `created_by`, `approved_by`, and `approved_at`.
- `office-service-mappings.schema.json`: `schema_version`, `release_version`, and records with office
  public ID, intent, department label, evidence URL, verification date, creator, approver and approval
  time.

Cross-file validation requires every mapping office to exist, every approved artifact record to have
a matching approval-manifest decision, reviewer/timestamps to equal the dataset approval, exact
19/3/10 counts and the named exclusions. The release verifier applies all four schemas and these
cross-file rules; malformed/reordered fixture cases are part of the focused tests.

### Canonical seed-owned DB projection

`seed_semantic_sha256` is computed by the repository generator, not by PostgreSQL. The hash input is
UTF-8 without BOM or trailing newline from Python
`json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False)`.
JSON null is literal `null`; booleans are lower-case JSON; dates are `YYYY-MM-DD`; timestamps are
normalized to UTC `YYYY-MM-DDTHH:MM:SSZ`; text is preserved without Unicode normalization.

The top-level object has arrays `kb_documents`, `kb_question_examples`, `offices`, and
`office_service_mappings`. Object keys are sorted by the serializer. Arrays are ordered by
`public_id`; `(kb_public_id, question_example)`; `public_id`; and `(office_public_id, intent)`
respectively, using Python Unicode code-point ordering. Nested `procedure_steps` and
`required_documents` retain approved source order. The included seed-owned fields are exactly:

- KB: `public_id`, `data_origin`, `category`, `service_name`, `answer_summary`, `procedure_steps`,
  `required_documents`, `processing_time`, `fee`, `department`, `source_title`, `source_url`,
  `last_verified_at`, `caution`, `status`, `created_by`, `approved_by`, `approved_at`.
- Question example: `kb_public_id`, `question_example`, `normalized_text` (initially null).
- Office: `public_id`, `data_origin`, `region`, `office_name`, `address`, `phone`, `opening_hours`,
  `map_url`, `source_title`, `source_url`, `last_verified_at`.
- Mapping: `office_public_id`, `intent`, `department_label`.

Generated UUIDs, `created_at`/`updated_at`, generated `is_official`, and release-only source/approval
fields not stored in the normalized DB are excluded from this DB projection. Their integrity remains
covered by the projected artifact hashes. The generator emits literal SQL expected-row CTEs from this
same projection. Seed and compensation compare each included column in both `EXCEPT ALL` directions
under the table locks; PostgreSQL does not need a digest extension. The repository verifier queries
the same fields after seed/replay, canonicalizes them with this algorithm, and compares the resulting
SHA-256 to the manifest evidence.

## 6. Projection transformation

### KB

- Include only manifest decisions `APPROVE_INITIAL_RELEASE` for `record_type=KB`.
- Preserve submitted official source/content fields and lexical public-ID order.
- Set `status=ACTIVE`, `data_origin=OFFICIAL`, `approved_by=PM-LOCAL-001`, and `approved_at` to the
  manifest `reviewed_at`. Preserve `created_by=AI-DATA-BACKEND`.
- Copy each approved record's 3..5 submitted question examples into `kb_question_examples` during
  import. These are authored official KB examples, not citizen questions.

### Offices

- Include only the three approved office records, preserve submitted OFFICIAL metadata and lexical
  public-ID order.
- The release JSON preserves author/reviewer/approval lineage. The current `offices` table retains
  public office fields, `data_origin`, source title/URL, verification date and generated `is_official`,
  but author/reviewer decision lineage remains release-only.

### Mappings

- Include only the ten `APPROVE_INITIAL_RELEASE` mapping decisions.
- Preserve department label, evidence source URL, verification date and author in the release.
- The existing DB table stores only office FK, intent and department label; the immutable release is
  the authority for mapping evidence/date/author lineage.

## 7. Generator and CLI

Use a dependency-free Python 3.12 module and thin CLI:

- `scripts/data_seed_release.py`: pure validation/projection/SQL serialization functions.
- `scripts/promote_data_seed.py prepare --draft-dir ... --release-version 0.1.0-initial.1 --released-at <ISO8601>`
- `scripts/promote_data_seed.py verify-release --release-dir data/official/releases/0.1.0-initial.1`
- `scripts/promote_data_seed.py activate-local-seed --release-dir data/official/releases/0.1.0-initial.1`
- `scripts/promote_data_seed.py verify-local-seed --release-dir data/official/releases/0.1.0-initial.1`

The production CLI accepts only the exact canonical draft and release paths and exact version
`0.1.0-initial.1`. It rejects absolute or relative aliases, symlink/junction/reparse components,
any other version, output outside the repository,
duplicate JSON members, stale approval/content hashes and noncanonical bytes before writing.

Publication is two recoverable phases, never represented as one cross-path atomic operation:

1. `prepare` builds every output in a repository-local temporary sibling, validates it, flushes files
   where the platform supports that operation, and publishes the complete immutable release directory
   by a same-parent rename. A failure before that rename leaves the release absent; a successful rename
   leaves a valid prepared release and never changes `supabase/seed.sql`.
2. `activate-local-seed` re-verifies the prepared release, writes a sibling temporary dispatcher,
   flushes it where supported, and atomically replaces only `supabase/seed.sql`. If replacement fails,
   it restores and verifies the prior dispatcher bytes while retaining the valid release as prepared
   but not locally active. Re-running activation for the same release is safe only when the dispatcher
   is already byte-identical; any unrelated drift fails closed.

Stable CLI output contains step IDs and issue-code counts only, never source/content/comment values.

## 8. Seed SQL contract

`seed.sql` is deterministic text generated from the release, wrapped in one transaction and fixed
lexical insertion order. It is not wired into `supabase db reset`: `[db.seed].enabled=false` remains
unchanged. The only supported importer is the future repository command
`powershell -File scripts/verify_data_seed.ps1 -ReleaseVersion 0.1.0-initial.1`. It first runs the
existing patched-CLI local migration gate, captures the local admin DSN in memory, and refuses it
unless its parsed identity is exactly user `postgres`, database `postgres`, host `127.0.0.1`, port
`54322`. It invokes the pinned release SQL through the existing locked Python/psycopg environment;
the DSN is never printed or persisted. Direct/manual execution is unsupported. The repository command
is an orchestration boundary only; SQL proves database/session/role facts and does not claim it can
identify the parent PowerShell process. The SQL:

1. Acquires a transaction-scoped advisory lock dedicated to DATA-SEED-001.
2. Before changing role, asserts `session_user='postgres'`, `current_user='postgres'`,
   `current_database()='postgres'`, and a `pg_auth_members` row granting `postgres` membership in
   `sejong_schema_owner` with `admin_option`, `inherit_option`, and `set_option` all true. It then
   executes `SET LOCAL ROLE sejong_schema_owner` and immediately asserts
   `session_user='postgres'` and `current_user='sejong_schema_owner'`. It fails closed if any
   assertion is false.
3. Acquires `ACCESS EXCLUSIVE` locks in a fixed order on `kb_documents`, `kb_question_examples`,
   `offices`, `office_service_mappings`, `interaction_events`, `failed_questions`, `kb_candidates`
   and `audit_logs`, under a bounded lock timeout. Existing application capabilities do not need to
   acquire the advisory lock: their table operations block behind these locks, and once they complete
   first the seed's locked preflight observes their rows and fails.
4. Fails before writes unless `kb_documents`, `kb_question_examples`, `offices`,
   `office_service_mappings`, `interaction_events`, `failed_questions`, `kb_candidates` and
   `audit_logs` are empty.
5. Inserts the 19 KB rows with ACTIVE/OFFICIAL and separate creator/approver metadata.
6. Inserts their official authored question examples.
7. Inserts 3 offices and resolves their generated UUIDs by stable `public_id` for 10 mappings.
8. Asserts exact post-insert counts, bidirectional exact canonical-column equality and excluded-ID
   absence before commit. The repository verifier separately computes `seed_semantic_sha256` evidence.

It uses explicit column lists and safely quoted literals. It never interpolates runtime user input,
uses no network function, logs no secret/question, and grants no new privilege. Reapplying to the same
database fails before mutation; reproducible replay means reset to a fresh migration-only DB and apply
the same release again.

## 9. Compensation and correction

`compensation.sql` is not a production rollback mechanism. It is a disposable-local verification
tool called only by the same `verify_data_seed.ps1` runner. It runs in one transaction under the same
advisory lock, role assertions and fixed-order `ACCESS EXCLUSIVE` table locks as the seed.

It fails before delete unless:

- all operational/reference tables (`interaction_events`, `failed_questions`, `kb_candidates`,
  `audit_logs`) are empty;
- the current seed-owned semantic projection exactly equals this release;
- no MOCK, unknown or later-release rows exist; and
- the caller is the asserted local migration session with `SET LOCAL ROLE sejong_schema_owner`.

Compensation uses the generated expected-row CTEs and bidirectional `EXCEPT ALL` comparisons defined
by the canonical seed-owned projection. It rejects any extra, missing or altered row, including a
same-public-ID content change. The repository verifier also recomputes `seed_semantic_sha256` before
and after the compensation/replay sequence for evidence; SQL equality, not a database digest
extension, is the destructive-operation guard.

On success it deletes mappings, offices and KB rows in FK-safe order; question examples cascade with
their KB. It asserts the release rows are absent before commit. Any precondition failure produces zero
deleted rows. A non-empty or released environment is corrected only by a new immutable release and a
separately approved migration/data transition, never by this compensation file.

## 10. Verification and acceptance criteria

### Pure/unit/contract

- RED→GREEN tests for PENDING, REJECTED, self-approved, stale hash, missing comment, wrong projection,
  WASTE-03 approval, weak mapping approval, mock inclusion and path/reparse attacks.
- Exact release projection 19/3/10 and exact excluded IDs.
- Byte-identical output on repeated generation in separate temporary roots with the same explicit
  inputs; no ambient clock, random ID or filesystem-order dependency.
- Existing release path, partial write and dispatcher drift all fail closed.
- Prepare failure before publish leaves no release; activation failure retains the verified prepared
  release and restores/verifies the prior dispatcher; reactivation is idempotent only for equal bytes.
- SQL escaping, explicit columns, transaction/advisory-lock/preflight/postcondition presence.

### Real disposable DB

- Fresh migrations → seed: exact 19 ACTIVE/OFFICIAL KB, 3 OFFICIAL offices, 10 mappings and authored
  question-example counts; citizen read capabilities expose only the 19 approved KB.
- WASTE-03, the two rejected mappings and mock rows are absent.
- Second seed attempt fails with zero row/count/canonical-projection-hash change.
- Forced mid-import failure rolls back every inserted row.
- Compensation succeeds only immediately after an isolated seed with operational tables empty.
- Seed → compensation → seed replay produces the same public IDs/content and capability results.
- Adding one interaction/audit/reference row makes compensation fail with zero deletion.
- Concurrent capability writes either complete before the exclusive locks and make the locked
  preflight fail, or block until seed/compensation finishes; no interleaving can create partial import
  or delete operational/reference data.
- Import through the supported `verify_data_seed.ps1` command proves role/session assertions;
  direct execution under a non-member/wrong principal fails before table access.

### Repository gates

- Existing 63-test DATA-001 approval suite remains green.
- DATA-SEED focused suite, pgTAP, backend integration, package/JSON/secret/runtime scans and
  `git diff --check` pass.
- `supabase/seed.sql` equals the release seed bytes.
- `versions/manifest.json.official_data` becomes `0.1.0-initial.1` only after release verification and
  real DB seed/compensation/replay succeed. DB schema and public API versions do not change.

## 11. Security, privacy, accessibility, performance and cost

- Security: exact approved hash-bound input, fail-closed paths, transaction/advisory and exclusive
  table locks, asserted local role/session, no new SECURITY DEFINER surface, grants, dynamic SQL or
  migration.
- Privacy: official public service/office data and authored generalized examples only; citizen raw
  text, PII, transcript, token, IP/device and provider payload remain absent.
- Accessibility: no UI change in this slice.
- Performance: only 19/3/10 local seed scale; measure generation/import duration but no new runtime
  latency target.
- Cost: Python standard library and existing PostgreSQL/Supabase local stack only; external API calls
  and additional dependency cost are zero.

## 12. Failure handling, recovery and handoff

- Generator failure before publish: delete only its verified temporary sibling; never delete or mutate
  an existing release. A successfully published release remains a valid prepared artifact even if
  activation later fails.
- Import failure: transaction rollback; verify zero partial rows before retry on a fresh DB.
- Dispatcher-copy failure: restore and byte-verify the prior tracked dispatcher; release remains an
  immutable prepared artifact, while `verify-local-seed` reports it inactive.
- Content correction after the initial release: new DATA-001 draft, PM approval, version and data
  transition design. This initial-release-only slice cannot replace an already seeded DB/dispatcher.
- Local DB recovery: migrations + the pinned official release recreate the dataset. Backups containing
  non-reproducible operational data belong to BACKUP-001 and are outside this design.
